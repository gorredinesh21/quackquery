How QuackQuery is built

One small FastAPI service, one embedded database, one LLM — and a guard in between. In plain language:

The pipeline

Your questionplain English
→
FastAPIvalidates & rate-limits
→
Catalogcolumns, types, samples
→
Geminiwrites one SQL query
→
Guardread-only SELECT only
→
DuckDBruns it (10s timeout)
→
Geminianswer + chart spec
→
SSEstreamed to you live

Self-correcting loop: if the SQL fails (or the guard rejects it), the error text goes back to Gemini for a repair pass — up to 3 repairs (4 attempts total). You see every attempt in the demo pipeline view; if all fail, the API returns the full SQL attempt trail. Cached questions (30 min TTL) skip straight to the answer.

Limits & guardrails

  • rate60 requests / minute per IP (sliding window)
  • retry3 LLM repair passes max (4 attempts total)
  • cacheidentical question + dataset cached 30 min
  • sizeCSV uploads up to 50 MB
  • time10 s hard timeout per SQL execution
  • rowsresponses capped at 200 rows (50 previewed in the UI)
  • guardsingle read-only SELECT — DML/DDL, PRAGMA, file functions and stacked statements are denied
  • scopesingle instance, in-memory caches (by design)

Stack & links

FastAPI serves the API and this site; DuckDB is the embedded analytical database (each dataset is its own table); Gemini 2.5 Flash on Vertex AI writes the SQL and the answers. A QUACK_LLM=mock mode runs the identical pipeline with zero API calls — that’s what the test suite (66+ tests) exercises.

What happens to your CSV

It is uploaded once, profiled once (types, nulls, sample values — see the Data page), stored as a table in the server’s DuckDB file, and used only to answer your questions. Nothing is sent to the LLM except column metadata, sample values, your question, and (for the answer step) a preview of the result rows. Delete the volume and it’s gone — there is no external database.
