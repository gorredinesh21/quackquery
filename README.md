# QuackQuery

**Ask your data anything.** Upload any CSV, ask a question in plain English,
and get back the SQL it wrote (auditable), the rows, and a chart spec —
streamed stage-by-stage over SSE, with a self-correcting LLM→SQL→execute
repair loop and a SELECT-only safety gate.

> Live demo: `https://quackquery-yzzxrxetcq-uc.a.run.app` · [API docs](https://quackquery-yzzxrxetcq-uc.a.run.app/docs) ·
> Run locally in 60 seconds — see [Run locally](#run-locally)

```
POST /api/datasets        (CSV)        POST /api/query  {dataset_id, question}
        │                                     │
        ▼                                     ▼
┌──────────────────────────────────────────────────────────────┐
│ FastAPI (uvicorn, single container, 512Mi, scale-to-zero)    │
│                                                              │
│  1. DuckDB: infer schema + stats + sample values (per column)│
│  2. Semantic catalog: LLM one-line column descriptions       │
│     (cached per dataset — upload pays for it once)           │
│                                                              │
│  query pipeline:                                             │
│    stage 1  retrieve catalog                                 │
│    stage 2  LLM: question → SQL   (schema + samples + rules) │
│    stage 3  GUARD: single read-only SELECT — deny-list for   │
│             DML/DDL, PRAGMA, COPY, ATTACH, file functions;   │
│             comments and string literals stripped first      │
│    stage 4  DuckDB execute — cursor-local TEMP VIEW `data`,  │
│             10s watchdog timeout                             │
│    stage 5  on error → LLM repair pass w/ error text          │
│             (max 3 retries → 422 + SQL attempt trail)        │
│    stage 6  LLM: plain-English answer + vega-lite chart spec │
│                                                              │
│  SSE: stage → sql → rows → chart → answer → done             │
│  result cache: sha1(dataset_id+question), TTL 30 min         │
│  per-IP sliding-window rate limit · X-Request-ID on every    │
│  response · structured JSON logs                             │
└──────────────────────────────────────────────────────────────┘
   DuckDB (embedded, file-based — no DB server anywhere)
   LLM: gemini-2.5-flash on Vertex AI (metadata-server auth on GCP,
        gcloud ADC locally, 429 Retry-After backoff) — or QUACK_LLM=mock
        for a zero-API deterministic mode
```

## What it is

- **Text-to-SQL API, not a chatbot.** Every answer ships with the exact SQL —
  results you can audit, not vibes.
- **Self-correcting pipeline.** Failed SQL (binder errors, guard rejections)
  is fed back to the LLM with the error text; up to 3 repair passes. The
  attempt trail is returned on failure.
- **Defense in depth.** A deny-by-default SQL guard (single SELECT statement,
  keyword + function denylist scanned on literal-stripped SQL) runs before
  anything touches DuckDB; queries execute against a cursor-local temp view.
- **Bundled demo datasets** (seeded, deterministic): Indian startup funding
  (217 rows), e-commerce orders (420), IPL matches (208).

## Why the guard is a real gate (not a prompt)

The LLM is *asked* to emit read-only SQL, but the guard *enforces* it:
stacked statements, `PRAGMA`, `read_csv()` escapes, `ATTACH`, CTE-wrapped
`DELETE`, `shell()` — all rejected before execution (34 unit-test cases in
`tests/test_guard.py`). Nothing generated by the model can write, read
files, or attach databases.

## Curl demo

```bash
# health + cache stats
curl -s localhost:8010/api/healthz | jq

# load the 3 bundled demo datasets (idempotent)
curl -s -X GET localhost:8010/api/datasets/demo | jq

# ask a question (JSON result: sql, rows, chart, answer, attempts)
curl -s -X POST localhost:8010/api/query \
  -H 'content-type: application/json' \
  -d '{"dataset_id": "<id-from-above>",
       "question": "top 5 sectors by total funding amount"}' | jq

# same question, streamed stage-by-stage (SSE)
curl -N -X POST localhost:8010/api/query/stream \
  -H 'content-type: application/json' \
  -d '{"dataset_id": "<id>", "question": "how many orders per payment method"}'

# upload your own CSV
curl -s -X POST localhost:8010/api/datasets -F file=@yourdata.csv | jq
```

SSE events arrive in order: `stage` → `sql` (per attempt) → `rows` →
`chart` → `answer` → `done` (or `error` with the full SQL attempt trail).

## Run locally

```bash
git clone https://github.com/gorredinesh21/quackquery && cd quackquery
pip install -r requirements.txt

# zero-API mode: deterministic rule-based SQL generator, no GCP needed
QUACK_LLM=mock uvicorn app.main:app --port 8010
open http://localhost:8010        # demo UI: dataset picker + question box

# with Gemini (needs gcloud auth; on GCP it uses the metadata server)
gcloud auth application-default login   # once
GCP_PROJECT=personal-project-dg21 uvicorn app.main:app --port 8010
```

Docker:

```bash
docker build -t quackquery .
docker run -p 8010:8080 -e QUACK_LLM=mock quackquery
```

## API

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/healthz` | liveness + dataset/cache stats |
| POST | `/api/datasets` | upload CSV (≤50MB) → `{dataset_id, schema, catalog}` |

| GET | `/` · `/docs` | demo page · public OpenAPI |

## Tests

```bash
QUACK_LLM=mock pytest -q          # 66 tests, ~6s, zero API calls
```

Coverage highlights: 34 guard cases (stacked/PRAGMA/file-function/CTE-smuggle
rejections), catalog type inference, upload validation, mock-LLM query flow,
guard-rejection → repair loop, exhausted-retries → 422 with attempt trail,
SSE event ordering, result cache, replay, per-IP rate limit, request-ID
propagation, and 10 golden (question → expected rows) pairs against the
seeded demo CSVs — plus 20 interleaved concurrent queries proving the
cursor-local `data` view never bleeds across datasets.

## Design notes / honest limits

- Single-instance by design (Cloud Run scale-to-zero, in-memory caches).
  Horizontal scale would need the store moved to GCS + a shared DuckDB
  read path — noted in the roadmap, not claimed as done.
- The catalog LLM runs once per dataset at upload, not per query.
- `data` is a cursor-local DuckDB TEMP VIEW — concurrent queries against
  different datasets are isolated by construction (tested).
- Storage is local-fs (DuckDB file + JSON registry); the store layer is a
  thin seam for a GCS backend later.

## Roadmap

- GCS-backed dataset store + shareable dataset URLs
- Multi-file joins (FK detection between uploaded CSVs)
- Semantic layer YAML (business metric definitions per dataset)
